# PROPOSAL — C4 Feeding (unit XP food)

<!-- author: AD-Gacha | raised: 2026-08-20 (B34) | status: BLOCKED ON DATA, not on code -->

## Why this is a proposal and not an implementation

B34 scoped C4 and found it blocked on **data that does not exist**, not on missing machinery:

| needed | exists today? |
|---|---|
| food items in `ItemCatalog` with a feed value | **NO** — `FeedValue` appears nowhere in the catalog |
| a unit XP curve (`MetaLevel` → XP required) | **NO** — no `AddTowerXP`, no curve anywhere in the Lobby |
| a writer for unit XP | **NO** — `UnitInstance.XP` / `.MetaLevel` have no writer outside defaults |
| the destroy/protect predicate | ✅ `Server.Meta.UnitConsumeRules` |
| the item-consumption path | ✅ `GrantService.SpendItems` (added B9 for ascension) |
| multi-select UI + confirm + toasts | ✅ B31–B33 (`SellButtons`, `UIKit.Confirm`, `UIKit.Notify`) |

Writing the service now would mean a remote that refuses every call because its config is empty, and
a config whose SHAPE is a guess — is food per-tier, per-stage, flat, or diminishing? Each answer
implies a different table. **A skeleton built against a guessed shape gets rewritten once the real
shape arrives, so the honest deliverable is this document plus the questions.**

## Proposed design

**One config, Lobby-local, `Configs.Meta.FeedConfig`** — same reasoning as `PlayerLevelConfig` at
B33: nothing in the Game reads it until the Game grants unit XP, and promoting a config with one
consumer buys a permanent drift obligation for nothing.

```lua
FeedConfig.XpForLevel(metaLevel)  -- what THIS unit level costs. The one curve.
FeedConfig.FeedValue(itemId)      -- XP a food item is worth. Reads ItemCatalog, never a second table.
FeedConfig.ApplyXP(level, xp, gained) -> newLevel, newXp, levelsGained   -- THE rollover rule
```

`ApplyXP` mirrors `PlayerLevelConfig.ApplyXP` deliberately: same signature, same bounded loop, same
"pure, returns, never writes" contract. Two rollover rules that look different is how two XP systems
end up rounding differently.

**One server rule, `Server.Meta.FeedRules`**, reusing what exists rather than restating it:

- the TARGET unit is protected by `UnitConsumeRules.Reason(...)` — feeding a locked or favourited
  unit is fine, but feeding one that is *gone* is not, so the `bad_uuid`/`not_owned` legs apply.
  **Note the asymmetry to settle:** selling destroys the unit, feeding destroys the ITEMS. The
  protections that stop a unit being destroyed should NOT block it being fed. This needs a separate,
  narrower predicate — reusing `IsConsumable` unchanged would be wrong.
- the FOOD is spent through `GrantService.SpendItems`, the existing single path.
- **credit first, destroy second** — the B31 ordering, for the same reason: `SpendItems` can refuse
  and an XP write cannot be undone.
- a `Quote(data, uuid, items)` that the preview, the refusal and the write all share (B9's lesson).
- `MaxBatch` on mass-feed, because a client can send any list it likes.

**One remote**, `Remotes.FeedUnit` (21 → 22), and the UI reuses the Units screen's existing
multi-select rather than growing a second selection mode.

## Open question already known

`STATE.md` carries **"a unit at `MAX_META_LEVEL` loses stored XP (`ApplyXP` discards it)"** against
AD-Game. Feeding makes that reachable by a player rather than theoretical: feeding a maxed unit would
silently eat the food. It should refuse instead, and that refusal belongs in `FeedRules`.

## What is needed to unblock

1. **Food items** — ids, names, tiers and XP values, added to `ItemCatalog` (shared canon, so this is
   an AD-Integration change).
2. **The unit XP curve** — same question answered for accounts at B33. `MetaLevel` caps and the cost
   per level.
3. **A decision on the source of food** — nothing grants items today except an INSANE victory (B20),
   so food would be unobtainable at launch even once fed-able.
