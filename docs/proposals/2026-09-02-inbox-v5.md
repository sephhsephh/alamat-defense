# Inbox — stored message history (needs schema v5)
<!-- from: AD-Meta/AD-Gacha | to: AD-Game (schema owner) | status: OPEN | 2026-09-02 (B48) -->

## The ask
Build the **Inbox** screen (the unwired `HUD.Right.UpperRight.InboxButton`): a listable history of
messages a player has received — login gifts, code rewards, dev grants, mail. This is the last of the
five upper-right HUD buttons still unbuilt (RedeemCodes B40, LeaderBoards B47, Settings live; Invite is
a SocialService prompt).

## Why this one genuinely needs a schema bump (checked B48)
The three previous meta systems that looked like they needed a bump did NOT — `LoginStreak`, `Quests`,
`ShopStock` and `Battlepass` were all already on `ProfileTemplate` since v2, unwritten. **Inbox is
different: there is NO inbox/mail/history field on the schema** (grepped B48; `MailService`'s own header
says so — mail today DELIVERS and reveals but stores nothing). A listable history has to be persisted,
so it is the first genuinely necessary bump since v4.

This is why it was deferred at B47/B48 rather than built: a v5 bump is **AD-Game's canon** (the schema
owner) and a **both-Place hard cutover** (like v4), not a Lobby-local change — too much to do unattended.

## The v5 field
```
Data.Inbox = { Messages = { { Id, Title, Body, Rewards?, Day, Read }, ... } }
```
- **CAPPED** (e.g. keep the newest ~30, drop the oldest on append) so the profile cannot grow without
  bound — the same discipline `Quests.Progress` pruning uses.
- `Id` is the message id; `Day` is a DAY NUMBER (invariant 3), never a timestamp. `Read` defaults false.
- `Rewards` (optional) mirrors GrantService's view shape so the screen can show what a gift contained.

## Migration (the AD-Game half — one session)
1. `ProfileTemplate.SCHEMA_VERSION = 5`; add `Inbox = { Messages = {} }` to `Template`.
2. `Migrations[4]` is a **DELIBERATE NO-OP**, exactly like `[2]` and `[3]` — `Reconcile()` runs before
   `Migrate()` and adds the new field, so no data migration is needed. **Never delete a no-op step**
   (`Migrate()` warns and STOPS at a gap, stranding every later one — STATE.md's standing rule).
3. Re-hash `ProfileTemplate` → mirror byte-identical to BOTH Places → update `shared/manifest.json` →
   re-verify 36/36 in both. The user republishes both Places (v5 hard cutover; v4 rejected after).
4. Teleport payload is unaffected (the Inbox is not teleported), so `MatchLaunchVersion` /
   `TeleportPayloadVersion` do NOT move.

## The build (the AD-Meta/AD-Gacha half — after the field exists)
- **`InboxService`** (Server, Lobby) — THE one writer of `Data.Inbox`. Remotes `GetInbox` (newest
  first) + `MarkInboxRead(id)`; an unread count for a badge (`PendingReveals` line ~116 already
  anticipated "a future inbox badge").
- **Append on delivery** — `MailDeliveryService` already does GRANT FIRST → `processed()` in one save;
  it ALSO appends `{Id, Title, Body, Rewards, Day, Read=false}` to `Data.Inbox.Messages` **in that same
  save**, **idempotent by `Id`** (mail is at-least-once; appending exactly once is the same trick that
  makes delivery exactly-once). Other sources (codes, login) can append the same way, or the Inbox can
  stay mail-only to start.
- **Screen** — a blockout `StarterGui.Inbox` + controller in the LeaderBoards/Quests pattern (row
  `MessageTemplate` Visible=false, cloned + filled; opens from the HUD button + `ClientEvents.OpenInbox`;
  read-only + mark-read). `RewardPush.ToOrQueue` still owns the LIVE reveal; the Inbox is the record.

## Cost / sequencing
Heavier than LeaderBoards (B47) because of the bump + both-Place publish; lighter than Phase D. Do the
AD-Game migration session first (or a combined session that owns both halves with the user present for
the republish), then the Lobby service + screen. Nothing else blocks on it.
